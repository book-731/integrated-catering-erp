# 第二階段 B 決策與範圍

版本 0.3.0。沿用既有 React／Express／Prisma 7／PostgreSQL，不新增其他業務模組。

## 本階段權限

| 功能               | ADMIN        | MANAGER      | CASHIER | KITCHEN  |
| ------------------ | ------------ | ------------ | ------- | -------- |
| 使用者管理         | 管理         | 無           | 無      | 無       |
| 食材及庫存唯讀資料 | 管理基礎資料 | 管理基礎資料 | 無      | 唯讀查詢 |
| 分類／餐點         | 管理         | 管理         | 查詢    | 查詢     |

舊矩陣將其他模組明列為草案。使用者已明確確認選項②：KITCHEN 可讀食材名稱、單位、庫存、安全庫存／低庫存提醒及製作足夠性；不可新增、修改、刪除、調庫存、改價格／配方、讀採購價格／供應商敏感資料、操作採購／使用者管理。本版依此授權後端 GET 並拒絕所有非讀取方法，不只是隱藏 UI。「使用者管理僅 ADMIN」不變。

所有寫入驗 Session、角色與 CSRF，交易內再鎖定並核對操作者是否仍啟用、版本相符且為 ADMIN／MANAGER。前端隱藏按鈕不代替後端驗權。

## 數值與單位

- stockQuantity、safetyStock、recipe.quantity 沿用 NUMERIC(14,3)，最多 11 位整數／3 位小數；price 沿用 NUMERIC(12,2)，最多 10 位整數／2 位小數。
- 請求為非負十進位字串，配方必須大於零；不接受 number、科學記號、前後空白、前導零或超精度，不隱式四捨五入。回應數量固定 3 位、價格固定 2 位。
- 後端 Prisma.Decimal 建構、比較與輸出，不用 JS 浮點數處理數量或金額。前端保持字串，不 parseFloat。
- unit 為 trim 後 1–20 字元的文字／數字，不含空白或符號。提供 g、kg、ml、L、個建議，也接受其他基礎單位。單位大小寫須完全一致，L 與 l 不互換；不提供自動換算。
- PUT 配方每列必須攜帶 ingredientId、quantity、unit；後端與食材當前基礎單位逐項核對。食材已有任何配方或非零庫存時不能改單位，包括停用餐點的關聯。

## 庫存及停用政策

新增食材庫存固定為資料庫預設 0。建立／修改 DTO 不含 stockQuantity 並以 strict schema 拒絕額外欄位。UI 明示唯讀與期初庫存待開發，沒有無流水的期初、調整、領料或銷售扣庫。

KITCHEN 可搜尋、狀態／單位／低庫存篩選與分頁。Ingredient DTO 明確白名單輸出，不包含採購／供應商欄位。唯讀 GET /menu-items/:id/ingredient-availability?servings=1 以 Repeatable Read + READ ONLY 交易取得當下配方及庫存，Decimal 計算 1–10000 整數份需求／不足量；canPrepare 亦要求餐點／分類／食材啟用、供應中、非空配方。沒有預留、扣庫、訂單或庫存流水寫入，reservation=false 不保證查詢後仍有貨。CASHIER 無此權。

所有基礎資料以 isActive 停用，沒有硬刪除 API。既有 Restrict FK 保護分類、食材及餐點關聯；配方保留，並帶出食材啟用狀態。

分類停用不級聯修改或刪除餐點；新餐點、改分類及重新啟用餐點須使用啟用分類。既有停用分類的餐點可以修改其他欄位，介面顯示分類已停用。isAvailable 是人工供應設定，不能據此視為已實作訂單可售驗證。

停用餐點的配方只讀。停用食材不能加入新配方或更改既有用量；可以原量保留或由管理者明確移除。不會自動刪除停用資料的關聯。

## 配方交易與併發

RecipeIngredient 沿用原多對多複合主鍵，沒有重建關聯表。GET 回傳完整配方與 version；PUT 是完整替換，可新增、修改、移除列或清空，最多 100 項。

PUT 必填 expectedVersion。單一交易驗權、餐點／食材狀態、單位與重複組合後，刪除舊列、插入新列並遞增 MenuItem.recipeVersion。任一步驟失敗整筆 rollback。相同舊版本的併發更新只有一個成功，其餘回 409，不採最後寫入覆蓋。

現階段單店目錄寫入採 PostgreSQL advisory transaction lock 12002002 串行，避免單位／停用／配方更新互相競爭。這是小型管理流量的明確取捨；未來高併發可改固定鎖定順序與細粒度 row locks，仍須保留原子性及版本檢查。完整配方查詢使用 Repeatable Read，確保版本及關聯用量一致。

本階段配方更新不建立歷史 revision 表。未來訂單需保存獨立不可變快照，不可直接讀取更新後的即時配方，規劃見 NEXT_ORDER_INVENTORY。

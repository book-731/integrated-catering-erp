## 四個既有腳本與新增準備腳本

### 本輪查出的時間偏移與Demo修正

Prisma目前安裝的adapter-pg在非UTC的PostgreSQL連線下會錯存／錯讀timestamptz時間，本輪於台北午夜後由真實SQL比對發現；先前畫面與API一致不足以證明底層時間正確。[Prisma官方倉庫問題28629](https://github.com/prisma/orm/issues/28629)也記錄此行為；本輪另確認了本機套件與實際DB時間，而非僅依網頁推論。

已在**專用Demo連線**加入`options=-c TimeZone=UTC`，不執行ALTER DATABASE／ALTER ROLE，不修改主.env或核心程式。新批次metadata為schema=2／sessionTimeZone=UTC；既有非UTC批次不再被stage沿用，舊展示資料保留，不回填時間。重啟套用後舊Session可能需要重新登入。報表比對新增午夜邊界、API時間與實際資料庫epoch完全一致、完成時間接近現在的檢查。

**原開發環境的非UTC時間風險尚未處理**：本輪不寫入原開發資料，不應盲目替所有歷史時間加8小時；資料庫預設now與應用程式寫入的時間可能不同。展示後需另做唯讀盤點、備份與核准的修復設計。因此明天只使用本頁UTC Demo，不切主開發環境。舊驗收ZIP不包含這次穩定性修正。

## 啟動失敗與安全復原

1. 確認在專案根目錄、Node24.x（至少24.11）／npm11；執行`npm run demo:start`，再開`http://localhost:5175/api/health`。一般PowerShell即可，不需重開資料庫設定。
2. 顯示服務部分失效或網頁無回應：等未完成送出結束，執行`npm run demo:restart`，重新整理登入頁並重新登入。專用程序全部停止後再`demo:start`的情境已實測。電腦開機不會自動啟動，仍要手動執行start；未實際重開整台Windows，不能宣稱已測完整重開機。
3. 不知道有沒有啟動成功：分別檢查3004 health與5175 api/health；若前者正常後者失敗，是前端／代理問題。`work/acceptance-demo/api.log`、`web.log`、`postgres.log`供本人檢查，勿把整份日誌或private.json貼到聊天。工具遇工作目錄所有權、陌生PID／連接埠占用會拒絕；不要taskkill不明程序。
4. 401或登入跳回：使用本頁Demo Email／本機密碼，固定localhost:5175，重新登入。403寫入：重新整理取新CSRF，再確認角色，不能關閉CSRF或擅自改權限。429依Retry-After等候；不要重複猜密碼、清限流表或關限流。
5. 「訂單已變更」：重新整理及搜尋該桌，檢查目前狀態再操作，不以新的表單連續重建訂單。庫存不足：選對本批餐點；不要直接改stockQuantity。期初已存在不能重做，應用合法採購入庫或改用備案。
6. 資料已被排練消耗：在上台前執行`npm run demo:stage`。它建立新批次且保留舊帳，不把原批次變回未收貨／未製作。不要刪work/acceptance-demo、private.json、OWNER.json或postgres資料目錄。
7. 找不到原生runtime：依WINDOWS_SETUP安裝固定版本；不要重新init既有cluster。當場沒時間修復則改用離線備案，不因Docker不可用而換庫。

**禁止**reset、truncate、drop、刪Volume、改已使用Migration、重設DB密碼、替換.env、盲目刪PID／資料目錄或Push。
